# 经营归因分析系统 · 云上数据存储方案

> 适用：本项目（`p2_attribution_analysis`）从本地 Docker 环境迁移到云服务器时的数据存储设计。
> 目标资源：单机 4C4G 起步（本项目按 2C2G 收敛），单库单实例，成本优先。

---

## 1. 现状盘点（数据存在哪）

| 数据类型 | 现状存储 | 介质 | 持久化方式 | 风险 |
|---|---|---|---|---|
| 业务库（bia：会话/消息/任务/结果/用户/数据源/LLM 记账） | MySQL 8.0 | 命名卷 `bia_mysql_data` | Docker volume（宿主机 `/var/lib/docker/volumes/`） | 服务器销毁/卷损坏即丢，无备份 |
| 场景示例库（scenario_goods / scenario_inventory，约 15 万行） | MySQL 8.0 同实例 | 同上 | 同上；可由 `scripts/gen_*` 重新生成 | 可重建，非核心资产 |
| WS 序列号 / 分布式锁（`ws:seq:{conv_id}`） | Redis 7 | 容器可写层（无卷） | **未开启 AOF，未挂卷** | 重启即全部丢失；仅影响 WS 去重，业务无损失 |
| 用户上传附件（csv/txt/md/xlsx…） | 文件系统 `data/uploads/{user_id}/` | bind mount `./data:/app/data` | 宿主机项目目录 | 服务器磁盘故障即丢 |
| 分析结果导出（markdown） | 文件系统 `data/exports/` | 同上 | 同上 | 同上 |
| agent 工作区文件（file_write） | 文件系统 `data/workspace/` | 同上 | 同上 | 同上 |
| JWT 签名私钥 | `secrets/oidc_rsa_private.pem` | bind mount `./secrets:/run/secrets:ro` | 项目目录（已 gitignore） | 丢失 → 全部已签发 JWT 失效 |
| 运行密钥（DB 密码 / OIDC_CLIENT_SECRET / APP_ENCRYPTION_KEY） | `.env` | 项目目录 | 文件 | 泄露 → 数据源密码可被 AES 解密 |

**结论**：MySQL 卷和 `./data` 是必须备份的资产；Redis 数据可丢但需开启 AOF 防 WS 错乱；密钥必须离线备份。

## 2. 上云存储架构（目标态）

```
┌───────────────────────── 云服务器（单机 Docker Compose） ─────────────────────────┐
│                                                                                  │
│   系统盘（60~100GB，SSD）                                                         │
│   ├── /opt/bia/                    项目部署目录（代码 + .env + secrets/）          │
│   └── Docker volumes               镜像层 + 容器层                                │
│                                                                                  │
│   数据盘（按需 100~200GB，SSD，独立云盘）  ← 数据全部收拢到独立挂载点               │
│   ├── /data/bia/mysql/             MySQL 数据目录（替代命名卷）                    │
│   ├── /data/bia/redis/             Redis AOF + RDB 目录                           │
│   └── /data/bia/appdata/           上传附件 / 导出结论 / agent 工作区              │
│                                                                                  │
│   云盘快照（策略：每日自动 + 每周保留 4 份 + 每月保留 2 份）                       │
└──────────────────────────────────────────────────────────────────────────────────┘
```

### 2.1 为什么把 MySQL 卷换成数据盘 bind mount

1. **可迁移**：命名卷深埋在 `/var/lib/docker/volumes/`，重建服务器时无法直接打包；bind mount 到 `/data/bia/mysql` 后，整盘快照 / rsync 一步到位。
2. **可快照**：独立云盘支持块级快照（分钟级 RPO 的兜底方案）。
3. **可扩容**：数据盘可在线扩容，系统盘通常不可。
4. **权限可控**：`chown mysql:mysql` 明确、可审计。

### 2.2 Redis 必须开启 AOF

Redis 存的是 **WS 单调递增序列号**（`ws:seq:{conv_id}`）。当前 compose 未开 AOF 也未挂卷，容器重建后序列号归零：

- 后果：WS 重连后客户端 `maxSeq` 基线高于服务端 → 新事件被当作旧事件丢弃 → **前端永远收不到流式更新（表现为"分析中但不出结果"）**。

修复（见 §5 必改项 #1）：`command: redis-server --appendonly yes --appendfsync everysec` + 挂载 `/data/bia/redis`。

## 3. 数据生命周期与备份策略

### 3.1 分层备份（3-2-1 原则的轻量落地）

| 层 | 工具 | 频率 | 保留 | 恢复时间 |
|---|---|---|---|---|
| L1 云盘快照（整盘） | 云控制台/API | 每日 03:00 | 7 份 | ~10 分钟 |
| L2 逻辑备份（mysqldump） | crontab + 脚本 | 每日 02:00 | 14 份 | ~30 分钟（可回表级） |
| L3 文件备份（uploads/exports/workspace） | crontab + rsync/tar | 每日 02:30 | 14 份 | ~15 分钟 |
| L4 异地（可选，成本敏感） | rsync 到对象存储（COS/OSS） | 每周 | 4 份 | 视网络 |

### 3.2 备份脚本（落盘即用）

保存为 `/opt/bia/scripts/backup.sh`，加入 crontab：

```bash
#!/bin/bash
# 每日 02:00 执行：MySQL 逻辑备份 + 应用数据打包 + 清理过期
set -euo pipefail
BK=/data/backups
TS=$(date +%F-%H%M%S)
KEEP_DAYS=14
mkdir -p "$BK"

# 1) MySQL 三库逻辑备份（用 root 走 socket 或 tcp 均可）
docker exec bia-mysql-1 sh -c \
  'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --routines --triggers \
   --databases bia scenario_goods scenario_inventory' \
  | gzip > "$BK/mysql-$TS.sql.gz"

# 2) 应用文件（上传/导出/工作区 + secrets + .env 脱敏版）
tar -czf "$BK/appdata-$TS.tar.gz" \
  -C /opt/bia \
  --exclude='node_modules' --exclude='.git' --exclude='data/uploads' \
  data/ secrets/ .env

# 3) 清理 14 天前
find "$BK" -name '*.gz' -mtime +$KEEP_DAYS -delete
echo "backup done: $TS"
```

crontab：

```cron
0 2 * * * /opt/bia/scripts/backup.sh >> /var/log/bia-backup.log 2>&1
```

### 3.3 恢复演练（验收恢复有效性）

```bash
# 场景：服务器重建后恢复
# 1) 挂载新数据盘到 /data，解包备份
# 2) 部署 compose，但先不启动 backend
docker compose up -d mysql redis
# 3) 恢复数据库
gunzip < /data/backups/mysql-latest.sql.gz | \
  docker exec -i bia-mysql-1 mysql -uroot -p"$MYSQL_ROOT_PASSWORD"
# 4) 恢复文件
tar -xzf /data/backups/appdata-latest.tar.gz -C /opt/bia
# 5) 启动全部
docker compose up -d --build
# 6) 验证
curl -s http://127.0.0.1:8080/api/health && docker compose ps
```

> 上线后第一个月每周做一次恢复演练，确认备份不是"看着有、恢复不了"。

## 4. 云服务器与云盘选型建议

| 项 | 建议 | 理由 |
|---|---|---|
| 实例规格 | 4C4G（本项目 2C2G 收敛，留一半余量给 LLM 在线路径） | backend 3 worker + MySQL 256M buffer pool |
| 系统盘 | 60GB 高效 SSD | 镜像 + 日志 |
| **数据盘（核心）** | **100GB 起步的 SSD 云盘，挂载到 `/data`** | 全部持久化数据收拢于此，可快照可扩容 |
| 云盘类型 | 高性能 SSD（生产）；容量型 SSD（演示/开发） | 随机 IO 由 MySQL 决定 |
| 网络 | 带宽 5~10Mbps 起步 | 单用户 Web 场景足够 |
| 备份 | 云盘自动快照（每日）+ 本脚本逻辑备份 | 双保险 |
| 安全组 | 仅放行 22 / 8080；3306/6379/8001 保持 127.0.0.1 | 与现有 compose 端口策略一致 |

## 5. 上线前必改项（按优先级）

### 🔴 P0（不修不可上线）

1. **Redis 持久化 + 挂卷**（docker-compose.yml）
   ```yaml
   redis:
     image: redis:7-alpine
     command: redis-server --appendonly yes --appendfsync everysec --maxmemory 128mb --maxmemory-policy allkeys-lru
     volumes:
       - /data/bia/redis:/data
   ```
   否则 WS 重连后序列号回卷，前端流式更新失效（§2.2）。

2. **MySQL 挂载到数据盘**（替代命名卷，可迁移可快照）
   ```yaml
   mysql:
     volumes:
       - /data/bia/mysql:/var/lib/mysql
       - ./scripts/mysql-init:/docker-entrypoint-initdb.d:ro
   ```
   首次部署时创建空目录并 `chown 999:999`（MySQL 官方镜像 uid），或直接使用初始化流程建卷后拷贝。

3. **备份脚本落地 + crontab + 首次恢复演练**（§3）。

### 🟡 P1（强烈建议）

4. **数据盘开启云盘快照**（控制台一键，日级）。
5. **`.env` 与 `secrets/` 离线备份**（本地保险箱/密码管理器），并生成强随机密钥替换现有值（当前 `.env` 中 LLM_API_KEY 为明文真实 Key，上线必须轮换）。
6. **上传文件大小与配额**已有 20MB 限制，确认云盘空间 ≥ 附件量增长（100GB 数据盘 ≈ 5000 个 20MB 附件）。

### 🟢 P2（体验优化）

7. `FLAG_COMMAND_EXEC=false`（生产禁止命令执行，compose 默认已 false）。
8. 前端反代已带安全头；如需公网 HTTPS，前置 Nginx/Caddy/CLB 终结 TLS，并同步修改 `OIDC_ISSUER` / `CORS_ORIGINS` / `OIDC_REDIRECT_URI` 为 https 地址。

## 6. 数据量估算与演进路径

| 数据 | 单条规模 | 月增估算 | 100GB 数据盘可用年限 |
|---|---|---|---|
| 业务库（消息/任务/结果） | 会话级 KB~MB | 1 千条提问 ≈ 50MB | > 10 年 |
| 场景库（15 万行） | ~200MB | 0 | — |
| 上传附件 | ≤20MB/个 | 演示期可忽略 | 取决于使用量 |
| 日志（task_logs / llm_calls） | 行级 | 数百 MB | 建议 90 天清理（PRD 已含） |

**演进路径**（单机不够时）：
1. 第一档：数据盘扩容 + 快照（零代码改动）；
2. 第二档：MySQL 换云数据库 RDS 托管（自动备份/高可用），Redis 换云 Redis；
3. 第三档：backend 无状态化（移除 `./data` 依赖，附件走对象存储 COS/OSS），前端 CDN。

## 7. 与部署运维文档的对齐

- 本方案是《部署运维文档.md》§5「生产上云清单」的数据存储细化；
- `cloud_deploy.sh` 已处理 .env 改写（APP_ENV/OIDC/CORS），未处理数据盘挂载与 Redis AOF —— **部署到新服务器前，先按本方案 §5 改 compose**，再跑 `bash cloud_deploy.sh`；
- `bia_migrate.sql`（11MB 快照）仅用于空库初始化，日常运维以 §3 备份为准，不要在生产用快照灌库覆盖增量数据。

# 上下文摘要压缩提示词（草案 v0.1）

> 关联 PRD：5.3 多轮追问与上下文管理
> 使用方式：每轮分析任务结束后调用一次（可复用同一 LLM 会话），输出写入 `context_summaries` 表（start_seq_no ~ end_seq_no）。
> 目的：防止多轮追问时上下文无限膨胀，用结构化摘要替代原始消息，保证后续追问的召回质量。

---

## 提示词模板

```
你是经营分析系统的上下文压缩器。请把下面【本轮对话】压缩为一段结构化摘要，
供后续追问时恢复上下文使用。

要求：
1. 只保留对后续分析有长期价值的信息，丢弃寒暄、过程性输出（工具调用细节可压缩为来源清单）；
2. 保留关键数字、表名/文件名、指标名与时间口径，不得改变原意；
3. 结论与证据要点必须可回溯到原文，不要引入原文没有的信息；
4. 总字数控制在 200 字以内；
5. 按如下 JSON 结构输出（不要输出其他内容）：

{
  "business_question": "本轮用户提出的业务问题（一句话）",
  "conclusion": "已得出的结论要点（含关键数字）",
  "evidence_sources": ["用过的证据来源，如表名/文件名/工具名"],
  "unresolved": "未决问题与待补充数据",
  "key_data_snapshot": "关键数据快照（不超过 5 条，如'近30天点击率 2.1%，环比 -0.6pp'）"
}

【本轮对话】
{conversation_turn}
```

## 服务端处理约定

1. 每轮结束生成摘要后，记录 `start_seq_no`/`end_seq_no` 为**本轮消息区间**，与摘要一并落库。
2. 追问时拼装上下文：最近 N 轮原始消息（可配置，默认 2 轮）+ 区间不重叠的摘要列表（按 end_seq_no 倒序取最近 M 条，默认 5 条）。
3. 若摘要压缩失败（LLM 返回非法 JSON），降级策略：保留最近 N 轮原始消息原文，不阻断追问流程，并记 WARN 日志。
4. 删除会话时级联删除对应 `context_summaries`。

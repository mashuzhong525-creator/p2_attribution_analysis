## 1. 技术选型决策表（概要设计评审，12 项）

| # | 决策项 | 决策 | 理由摘要 |
|---|---|---|---|
| 1 | ORM | **SQLAlchemy 2.0 异步 ORM**（asyncmy 驱动） | 与 FastAPI 异步栈一致；WS/Agent 期间不阻塞事件循环；Alembic 兼容 |
| 2 | 任务队列 | **进程内 asyncio 队列**（`asyncio.Queue` + 3 worker 协程） | 2C2G 单 worker 固定；零额外依赖；取消=协程 cancel 即时生效 |
| 3 | Agent 引擎位置 | **backend 进程内**（异步任务运行） | 工具调用与 WS 推送共享内存态；内存预算 600MB 已含此设计 |
| 4 | 后端模块划分 | **领域垂直切片**（auth/chat/attachment/task/agent/result/admin + core） | 域内内聚、跨域解耦；与 M1~M4 里程碑对应 |
| 5 | JWT 校验 | **本地验签 + JWKS**（auth 暴露 `/.well-known/jwks.json`，backend 拉公钥缓存） | 零网络往返；auth 宕机不影响已登录会话；两服务解耦 |
| 6 | WS 信封 | **统一信封 + seq 序号** `{v, type, conversation_id, task_id?, seq, ts, payload}` | seq 用于去重/乱序检测；协议可版本演进 |
| 7 | 断线恢复 | **REST 恢复 + WS 增量**（重连后客户端拉会话历史/任务/结果重建 UI） | 幂等可靠；断线期事件靠 REST 兜底不丢 |
| 8 | LLM 流式 | **规划非流式 + 结论流式**（规划步快速拿 tool_call，结论步边到边） | 兼顾速度与体验；Agent 应用事实标准 |
| 9 | 前端 Store | **按域拆分 6 个**（chat/message/task/result/ws/admin） | 职责单一；与后端域一一对应，可并行开发 |
| 10 | 前端 WS | **自研轻封装**（重连退避 + 心跳 + 信封分发 + seq 去重，约 200 行） | 协议完全对齐；无第三方依赖 |
| 11 | 示例数据 | **固定种子生成脚本**（seed=2026，批量 INSERT） | 确定性可复现；演示故事线可控不翻车 |
| 12 | 命令沙箱 | **subprocess 工作区沙箱**（cwd 限定 + 白名单命令 + 黑名单 + 超时强杀 + 输出截断） | 2C2G 下最轻；功能开关可整体禁用 |

### 2.2 进程与容器

| 容器 | 进程 | 职责 |
|---|---|---|
| `backend` | uvicorn 单 worker | REST API + WS 端点 + Agent 引擎 + 异步任务队列 |
| `auth` | uvicorn 单 worker | OIDC Server：authorize/token/userinfo/jwks/well-known |
| `mysql` / `redis` / `frontend(nginx)` | 同 PRD 4.3 | 数据 / 缓存 / 静态资源+反代 |

> 约束：Agent 引擎与 API 同进程 → 任务并发受单进程事件循环限制，硬上限 ≤3 运行任务（信号量），超限排队/拒绝。

> 密钥管理：RSA 密钥对由 auth 启动时生成（无持久化则重启后 backend 拉新公钥）；生产可注入持久化私钥文件。JWT 签名算法 RS256。

### 3.3 数据库访问

- **引擎**：`create_async_engine("mysql+asyncmy://...")`，连接池 `pool_size=5, max_overflow=5`（对齐 MySQL `max_connections=50`，业务+auth 两服务合计 10~15 连接）。
- **Session**：`async_sessionmaker`，FastAPI 依赖注入 `get_db`（每请求一 session）。
- **UUIDv7**：`uuid7` 库（或自实现），应用层生成，VARCHAR(32) 无横线。
- **软删**：`SoftDeleteMixin`（`deleted_at`），DAO 层默认过滤 `deleted_at IS NULL`。
- **迁移**：Alembic，基线 `0001_initial` 建 17 张表；启动时 `alembic upgrade head`，失败则健康检查不过（PRD 9.7）。

### 3.4 异步任务队列（task 域）

```
启动时：创建 asyncio.Queue(maxsize=10) + 3 个 worker 协程 + 信号量(3)

提交：POST /api/chat/send
  → 互斥校验（会话无 running 任务，PRD 6.5）
  → 创建 message(seq_no) + analysis_task(queued)
  → queue.put(task_id)（满则 429 提示稍后再试）

worker 循环：
  task_id = await queue.get()
  → 更新 running → 调用 agent.engine.run(task)（含 LLM 调用与工具执行）
  → 更新终态（success/failed/cancelled）
  → 推送 done

取消：WS cancel_task 或 POST /api/tasks/{id}/cancel
  → 校验任务非终态
  → task 协程 cancel()：LLM 流 aclose()、子进程 terminate()
  → 状态置 cancelled + error_message=「用户取消」
```

### 3.5 Agent 引擎设计（agent 域）

**引擎循环（对齐 PRD 5.2 + 概要设计决策 8）：**

```
engine.run(task_id):
  1. 装配上下文：会话摘要(context_summaries 最近区间) + 附件 parse_result_json
     + 数据源 schema 描述 + 场景说明 + 工具清单 + 六段式模板（prompts.py 组装）
  2. 规划步（非流式 LLM，tools=registry.schema()）：
     ├─ 返回 tool_calls → 执行第 3 步
     └─ 返回最终六段式 JSON → 跳第 5 步
  3. 工具执行（循环，步数上限 8 / 总时长 10 分钟，均可配置）：
     逐个 tool_call：参数校验 → 推送 tool_start → 执行（安全约束见 §6）
     → 推送 tool_finish（含结果摘要）→ 结果作为 tool 消息回传
     → 再次规划（非流式）…直到 LLM 输出最终答案
  4. 超限兜底：步数/时长超限 → 基于已有证据尽力输出部分结果 + 标注 missing_data
  5. 六段式校验（Pydantic 模型）→ analysis_results 落库
     → result_markdown 生成 → result_generate 写文件 → 推送 result_ready
  6. 摘要压缩（summarizer.py，引用 context-summary-prompt.md）→ context_summaries 落库
  7. 每步 LLM 调用写 llm_calls 一行（模型/token/latency/cost，按配置单价计费）
```

**LLM 客户端（llm.py）：**

| 调用类型 | 方式 | 用途 |
|---|---|---|
| 规划调用 | `chat.completions.create(stream=False, tools=...)` | 拿 tool_calls 决策，快、省 token |
| 结论调用 | `chat.completions.create(stream=True)` | 六段式生成，增量经 WS 转发（message_delta） |
| 摘要调用 | 非流式 | 上下文压缩（独立小调用，不计步数） |

- base_url/api_key/model 全部来自 system_configs（`llm_base_url`/`llm_api_key`/`llm_model`），管理后台热更新后新任务生效。
- 流式转发：本地只透传文本增量（约 20~50 字/块），不聚合全文，2C2G 内存友好（PRD 11.1）。
- 取消：`response.aclose()` 终止流；记录 llm_calls.status=failed。

**工具注册表（tools/registry.py）：**

```python
class Tool(BaseModel):
    name: str
    description: str
    parameters: dict          # JSON Schema
    async def execute(self, ctx: ToolContext, **kwargs) -> ToolResult: ...

class ToolRegistry:
    _tools: dict[str, Tool]
    def register(tool): ...
    def schema() -> list[dict]      # 供 function calling tools 参数（引用 tool-descriptions.md）
    async def run(name, **kwargs) -> ToolResult   # 执行前统一校验+审计
```

## 4. 认证设计

### 4.1 授权码流程时序

```
浏览器            frontend(nginx)   backend            auth(OIDC)       业务库
  │ GET /auth/login   │               │                   │                │
  │──────────────────▶│               │                   │                │
  │                   │ 302 Location: auth/authorize?...  │                │
  │◀──────────────────│               │                   │                │
  │ 302 → auth/authorize?client_id&redirect_uri&scope...  │                │
  │──────────────────────────────────────────────────────▶│                │
  │                   │               │  校验 client_id/redirect_uri       │
  │ 显示认证中心登录页 │               │  密码校验 → 发 code（5 分钟）        │
  │◀──────────────────────────────────────────────────────│                │
  │ 302 → backend/auth/callback?code=xxx                   │                │
  │──────────────────────────────────────────────────────▶│                │
  │                   │               │ POST /token(code) ──▶│              │
  │                   │               │◀─ access+refresh ──│              │
  │                   │               │ 验 JWT 签名（JWKS 公钥）            │
  │                   │               │ GET /userinfo ─────▶│              │
  │                   │               │◀─ sub/role ───────│              │
  │                   │               │ users upsert（external_user_id）    │
  │                   │               │ 种 HttpOnly Cookie（access 15min）  │
  │ 302 /chat  ◀──────│               │ refresh 存 HttpOnly Cookie(7d)     │
  │◀──────────────────│               │                   │                │
```

### 4.2 JWT 本地验签（决策 5）

- auth 暴露 `/.well-known/jwks.json`（RS256 公钥）。
- backend 启动时拉取公钥缓存；验签失败（密钥轮换）自动重拉一次。
- 请求鉴权：Cookie（HttpOnly）或 Authorization: Bearer → 本地验签（签名/过期/aud）→ 取 sub → 查/缓存 users 记录。
- 刷新：access 过期 → 前端 401（AUTH_EXPIRED）→ 调 `/auth/refresh`（带 refresh Cookie）→ 换新 access → 重放请求。

### 4.3 用户同步

- 首次登录 upsert：`users.external_user_id = auth sub`，username/display_name/role 同步，更新 `last_login_at`。
- 角色变更以 auth 中心为准（登录时同步覆盖）。

## 5. 实时通道设计（WS）

### 5.1 统一信封（决策 6）

```json
{
  "v": 1,
  "type": "message_delta",
  "conversation_id": "01J2X...",
  "task_id": "01J2Y...",
  "seq": 42,
  "ts": "2026-08-18T07:00:00Z",
  "payload": { "delta_text": "综合来看，" }
}
```

- `type`：对齐 PRD 8.4（message_start/message_delta/tool_start/tool_finish/task_status/result_ready/error/done/attachment_parsed/ping）。
- `seq`：会话内单调递增事件序号，Redis `INCR ws:seq:{conversation_id}` 分配（从 1 起）。**与 messages.seq_no 不同源**：seq_no 是落库消息序号（回放用），ws seq 是事件流序号（去重用），两者都单调递增。
- 客户端去重规则：维护已处理最大 seq；`seq ≤ max` 丢弃；`seq = max+1` 渲染；`seq > max+1` 缓存排序后按序渲染（乱序保护）。

### 5.2 发送消息全链路时序（含补充接口 POST /api/chat/send）

```
Frontend                 backend                    auth/Redis        LLM API
  │ POST /api/chat/send   │                            │                │
  │ {conversation_id,     │ 互斥校验(会话无 running)     │                │
  │  content}             │ message 落库(seq_no)        │                │
  │──────────────────────▶│ analysis_task(queued) 落库  │                │
  │ {message_id, task_id} │◀───────────────────────────│                │
  │                       │ queue.put(task_id)         │                │
  │                       │ worker: task→running       │                │
  │◀──── WS message_start─│                            │                │
  │                       │ 规划调用(非流式, tools) ──────▶│               │
  │                       │◀──── tool_calls ───────────│                │
  │◀──── WS tool_start ───│ db_query 执行              │                │
  │                       │◀── 结果 ──(SQLite→MySQL)    │                │
  │◀──── WS tool_finish ──│ (含结果摘要)                │                │
  │                       │ … 循环至收敛                │                │
  │                       │ 结论调用(流式) ──────────────▶│               │
  │◀──── WS message_delta─│ 逐块转发                    │                │
  │                       │ 六段式 JSON → 校验 → 落库    │                │
  │                       │ result_markdown → 文件      │                │
  │◀──── WS result_ready ─│                            │                │
  │◀──── WS done ─────────│ task→success + 摘要压缩     │                │
```

> **补充接口（PRD 8.2 缺项）**：`POST /api/chat/send`，入参 `{conversation_id, content}`，响应 `{message_id, task_id}`。此接口是"消息发送→任务创建"的入口，PRD 表格遗漏，概要设计正式补充，验收映射不变（验收项 2/3 依赖此接口）。

### 5.3 取消时序

```
Frontend                 backend
  │ WS cancel_task        │
  │ {task_id}             │
  │──────────────────────▶│ 校验任务 running
  │                       │ 协程 cancel：LLM 流 aclose()
  │                       │ 子进程 terminate()（command_exec 中）
  │                       │ task → cancelled
  │◀──── WS task_status ──│ {task_status: cancelled}
  │◀──── WS done ─────────│ {finished_at}
```

### 5.4 心跳与断线恢复（决策 7）

- 心跳：服务端 30s ping → 客户端 pong；连续 2 次未 pong 判定断线，清理连接。
- 重连：客户端指数退避（1s → 2s → 4s → … → 30s 封顶）；重连前重新调 `POST /api/chat/ws-token` 换取新一次性令牌。
- 恢复：WS 重连成功后，客户端并行拉 REST：
  - `GET /api/chat/ls/{conversation_id}`（历史消息）
  - `GET /api/tasks/{task_id}`（任务状态/步骤）
  - `GET /api/results/{task_id}`（结果，若已有）
  重建 UI 后，WS 增量正常接收（seq 去重防重放）。

## 6. 安全实现要点

### 6.1 数据库工具安全（db_query）

- 连接：示例库/外部数据源均用**只读账号**（MySQL `GRANT SELECT`）；外部源由管理员配置。
- SQL 校验链：去注释 → 正则白名单（`^SELECT\s`，禁止 `;` 多语句、`INTO OUTFILE`、`LOAD_FILE`）→ 强制追加 `LIMIT 500`（无 LIMIT 时）→ 超时 30s（`asyncio.wait_for`）。
- 表白名单：示例库白名单（10 张场景表）；外部源由管理员在数据源配置里声明允许表。

### 6.2 命令沙箱（决策 12）

- 执行：`asyncio.create_subprocess_exec`，`cwd=workspace/{user_id}/{conversation_id}`，无 shell（`shell=False`，参数数组直传，杜绝注入）。
- 白名单命令：`python3`（仅数据分析脚本）；黑名单关键词（`rm -rf`、`curl`、`wget`、`nc`、`mkfs` 等，对 argv 逐项检查）。
- 超时 60s 强杀（`terminate` → 3s 后 `kill`）；stdout/stderr 合并截断 64KB；退出码非 0 记 error。
- 功能开关 `flag_tool_command_exec`（默认开，生产可整体关，PRD 6.6.4）。

### 6.3 文件与附件安全

- 所有路径 `os.path.realpath` 规范化后校验前缀 ∈ {uploads, exports, workspace} 对应会话目录；拒绝 `..` 逃逸与符号链接越界。
- 附件：类型白名单（csv/xlsx/txt）+ 20MB 上限（可配置）+ MIME 与扩展名双重校验。

### 6.4 密钥与审计

- 数据源密码 AES-256-GCM 加密，密钥走环境变量（backend 启动注入）。
- auth 用户密码 argon2/bcrypt 哈希。
- 管理写操作（配置/数据源/开关）写 audit_logs（before/after JSON + ip + user_agent）。

### 7.2 Pinia store 拆分（决策 9）

| store | 状态 | 动作 |
|---|---|---|
| `chatStore` | conversations、currentConversation | create/list/rename/delete/switch |
| `messageStore` | messages（按 seq_no 排序）、lastSeqNo | loadHistory/append/applyDelta |
| `taskStore` | currentTask、status、step、cancelling | setStatus/setStep/cancel |
| `resultStore` | currentResult、exporting | load/export/download |
| `wsStore` | connected、reconnecting | connect/reconnect/dispatch（按 type 分发到各 store） |
| `adminStore` | configs/dataSources/logs/flags | fetch/update/reload/testConnection |

跨 store 协作：wsStore 收到事件 → 按 type 调对应 store 的 action（如 `result_ready` → resultStore.load）。消息增量 `message_delta` 由 wsStore 直接交给 messageStore.applyDelta。

### 7.3 WS 客户端封装（决策 10）

```
class WsClient:
    connect(conversation_id)      # 取 ws_token → 建立连接
    # 自动重连：指数退避 1s→30s，重连前重新取 token，回调 onReconnected（触发 REST 恢复）
    # 心跳：30s 收到 ping → 回 pong；超时判定断线
    # 信封解析：校验 v/type/seq → seq 去重/乱序缓存 → 按 type emit 事件
    # 事件订阅：on('message_delta', cb) / on('tool_start', cb) / ...
    cancelTask(task_id)           # 发送 cancel_task
    close()
```

### 7.4 流式渲染

- `message_delta` 追加到当前 assistant 消息文本缓冲区，`requestAnimationFrame` 节流更新 DOM（避免每块重渲染）。
- 工具卡片：`tool_start` 插入卡片（running 态）→ `tool_finish` 更新摘要与状态徽标；同一任务内按到达序排列。
- 结果区：`result_ready` 后拉 `GET /api/results/{task_id}` 渲染六段式（或直接用 payload 渲染，失败降级 REST）。
- 历史回放：进入会话调 `GET /api/chat/ls/{id}`，按 role/message_type 分别渲染气泡/工具卡片/结果。
